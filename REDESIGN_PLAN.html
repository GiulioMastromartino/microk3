MicroK3 v2.0 — Full Redesign Plan

From a monolithic Flask dashboard to a modular, real-time micro-ROS control & monitoring platform.

Document type: Design RFC Status: For review Scope: microrosWs/microk3 Date: 2026-06-25

1Executive Summary

MicroK3 today is a single app.py (~1,080 lines) that bundles Flask routing, global mutable state, ROS-update dispatch, metrics serialization, auth, and persistence into one module. It works — nodes are discovered, heartbeats are processed, latency is measured, and a dashboard renders — but the monolith has reached the point where every new feature (more node types, real-time push, persistence beyond a JSON file, multi-user) fights the existing structure.

This document proposes a full but incremental redesign to v2.0, guided by three moves:

① Decompose

monolith → layers

Split app.py into an application factory, Blueprints, a typed StateStore, a ROS service, and a persistence layer. No business logic in route handlers.

② Push, don't poll

setInterval → SSE/WS

Replace the 1–3 s polling loops with a real-time transport (Server-Sent Events first, WebSocket optional) so the dashboard reflects node state the instant ROS publishes it.

③ Formalize contracts

dicts → typed models

Replace ad-hoc dicts crossing the ROS↔Flask boundary with Pydantic/dataclass events, a schema'd persistence layer (SQLite), and an OpenAPI-documented API.

⓵ What stays

The ROS topic contract (microk3/node_status, microk3/system_alerts, microk3/performance_metrics, microk3/commands), the micro-ROS agent deployment, the time-sync / latency math in the Renode bridge, and the overall product UX. The redesign is about how the backend is organized and how data moves, not rewriting the embedded protocol.

2Current State

2.1 What MicroK3 is

A Flask 3.0 + rclpy service, containerized with the micro-ROS agent and a Renode simulation bridge, that:

  • Discovers STM32 micro-ROS nodes via heartbeat messages on microk3/node_status.
  • Measures client→agent→ROS latency, jitter, bandwidth, and clock-sync offset (the heavy lifting lives in tools/renode_heartbeat_bridge.py, ~690 lines).
  • Surfaces everything through server-rendered Bootstrap templates + a polling JS layer + a read-mostly REST API.
  • Inspects the live ROS graph and lets operators watch arbitrary topics dynamically.

2.2 Pain points (the "why")

Architecture

  • God module. app.py owns routing + global state + a 140-line ros_update_callback switch.
  • Global mutable dict system_data read/written from the ROS thread, the Docker thread, and request handlers under a mix of locks — race-prone.
  • No service boundary between "ingest ROS events" and "serve HTTP".

Real-time UX

  • Polling everywhere: 2 s for metrics, 1 s for topic samples, 3 s for graph — 3 concurrent loops per open tab.
  • No push. Failures & offline transitions appear only on next poll.
  • Full re-render of watched-topic cards every second.

Data & correctness

  • Persistence is effectively dead — load_system_data() deliberately ignores the JSON file. State is lost on restart.
  • Stringly-typed latencies like "C->A 3.200 ms | A->ROS ..." baked onto the Node model for the template.
  • Failure IDs = len(list)+1 → collisions after deletes.

Operability

  • Node logs = regex over a flat log file (get_node_log_lines) — doesn't scale, no rotation awareness.
  • Single hardcoded admin in env vars; no roles, no audit trail for who changed what.
  • No health depth — /health is a static "healthy"; no readiness vs. ROS connectivity.
⚠ Not a rewrite-from-scratch

The embedded firmware, the ROS message contract, and the bridge's clock-sync algorithm are valuable and correct. The redesign reuses them verbatim and only re-houses the Python backend. Goal: ship incrementally with a working dashboard at every step.

3Principles & Goals

Design principles

  1. One responsibility per module. Route handlers validate & delegate; they never mutate shared state directly.
  2. Typed boundaries. Events crossing the ROS↔HTTP boundary are validated dataclasses/Pydantic models, not bare dicts.
  3. Single source of truth. A StateStore owns all runtime state behind one locked façade.
  4. Push first. New data flows to clients via events; polling endpoints remain for compatibility only.
  5. Configurable, not hardcoded. Watch limits, intervals, history sizes move to config.
  6. Testable in isolation. Every layer runs without ROS / Docker / hardware.

Concrete goals (v2.0)

  • Sub-second event propagation ROS → browser.
  • State survives container restart (SQLite-backed).
  • Pluggable node/bridge adapters (STM32 hardware, Renode, future boards) behind one interface.
  • OpenAPI-documented API + Swagger UI.
  • Structured JSON logging; per-node structured event log.
  • ≥80% unit-test coverage of non-ROS logic.
  • Same Docker UX (docker compose up), zero firmware changes.

4Target Architecture

Four horizontal layers, with events flowing top-to-bottom and queries bottom-to-top:

⓶ The key invariant

Only the StateStore mutates runtime state. Adapters ingest events; transport layers read snapshots or subscribe to an EventBus. No route handler ever touches system_data directly — eliminating the current locking jumble.

5Backend Redesign

5.1 Application factory + Blueprints

Replace the module-level side effects in app.py with a factory. This makes testing, multiple configs, and WSGI servers (gunicorn) first-class — and fixes the latent bug where the ROS thread only starts in __main__ (today, running under gunicorn silently skips ROS).

# microk3/app_factory.py
def create_app(config_name="development"):
    app = Flask(__name__, template_folder="templates")
    app.config.from_object(get_config(config_name))

    # Single shared core
    store   = StateStore(persistence=SqliteStore(app.config["DB_PATH"]))
    bus     = EventBus()
    ros     = RosService(store=store, bus=bus)
    metrics = HostMetricsService(store=store, bus=bus)

    app.extensions.update(store=store, bus=bus, ros=ros, metrics=metrics)

    app.register_blueprint(web_bp)          # server-rendered pages
    app.register_blueprint(api_bp)           # /api/* (OpenAPI)
    app.register_blueprint(sse_bp)           # /events SSE stream
    app.register_blueprint(auth_bp)          # /login, sessions, roles

    register_lifecycle(app, ros, metrics)   # start/stop on app context
    return app

5.2 The StateStore (single source of truth)

A thread-safe façade replacing the global system_data dict and the scattered ros_state_lock usages. It takes typed events in and yields immutable snapshots out.

@dataclass(frozen=True)
class SystemSnapshot:
    nodes:    tuple[Node, ...]
    failures: tuple[Failure, ...]
    status:   SystemStatus
    metrics:  MetricsSnapshot
    ros:      RosGraphSnapshot
    updated_at: datetime

class StateStore:
    def apply(self, evt: Event) -> list[Event]:
        # one RLock; validates, mutates, persists (debounced), returns derived events
    def snapshot(self) -> SystemSnapshot: ...     # deep, frozen copy for readers
    def watch(self, topic) -> Result: ...          # delegates to RosService
Why immutable snapshots?

Templates and SSE serializers receive a frozen copy they can iterate freely — no lock held during rendering, no risk of a half-updated dict leaking into JSON. This alone removes the most fragile pattern in the current code.

5.3 Persistence (SQLite)

Replace the dead JSON file with a tiny SQLite DB (zero-ops, file-based, in-volume). Two goals: survive restarts, and give failures/tasks real primary keys.

CREATE TABLE nodes (
    id INTEGER PRIMARY KEY, name TEXT, type TEXT,
    status TEXT, health INTEGER, first_seen TEXT, last_seen TEXT);
CREATE TABLE failures (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    node_id INTEGER, ts TEXT, level TEXT, description TEXT);
CREATE TABLE metric_samples (   -- ring buffer, pruned by age
    ts TEXT, node_id INTEGER, payload TEXT);

Metrics history is already a bounded ring in memory; SQLite just persists the latest snapshot periodically so the dashboard doesn't start empty after a restart. Node/failure tables are authoritative.

6ROS Integration Layer

The current ros_interface.py is the cleanest part of the codebase — it stays, but gains a typed contract and is wrapped by a thin RosService that talks to the StateStore instead of a raw callback.

6.1 Replace the callback switch with typed events

Today, ros_update_callback(action, data) is a 140-line if/elif over string actions. v2.0 makes the RosService emit the specific Event types the StateStore already understands:

Today (string action)v2.0 typed eventHandler
'update_node'NodeStatusEventStateStore.apply
'add_failure'FailureEventStateStore.apply
'raw_heartbeat'RawHeartbeatEventstructured logger
'performance_metrics'MetricsEventStateStore.apply
'graph_snapshot' / 'topic_sample' / 'watch_*'GraphEvent / TopicSampleEvent / WatchEventStateStore.apply

6.2 Bridge ↔ Dashboard contract stays identical

The microk3/* topics remain the wire format. The RosService still subscribes to microk3/node_status, microk3/system_alerts, microk3/performance_metrics and publishes microk3/commands. No firmware change required.

6.3 Graceful degradation

rclpy import is already optional; RosService formalizes a NullRosService stand-in so the whole app runs (and most tests run) without ROS installed.

7Bridge Refactor

tools/renode_heartbeat_bridge.py (688 LOC) is one RenodeHeartbeatBridge node doing five jobs: time-sync master, heartbeat watchdog, latency telemetry, position telemetry, and a metrics publisher. The math is correct and is not rewritten — it is extracted into reusable, unit-testable modules:

Extracted moduleMoves outWhy

bridge/telemetry.pyTopicTelemetryState (latency / jitter / bandwidth / rate)Already nearly standalone; promote to first-class

⓷ Generalize to an adapter interface

The bridge becomes the reference implementation of a NodeAdapter protocol. Adding a real-hardware STM32 adapter (no Renode heartbeat) or a second simulated board later means implementing the same interface — no dashboard changes.

8Real-Time Transport

The single highest-impact UX change. Replace the three polling intervals with a push channel.

Phase 1 — Server-Sent Events (recommended)

  • One-way, trivial over plain HTTP, auto-reconnect built into the browser EventSource API.
  • GET /events streams a typed event stream: node.changed, failure.logged, metrics.updated, topic.sample, graph.changed.
  • Client keeps a tiny in-memory store; applies patches; re-renders only affected components.
  • No new dependency, no WebSocket proxy/ingress concerns.

Phase 2 — WebSocket (optional)

  • Only if we later need client→server commands over the same socket (e.g. ack failures, drag-to-reorder).
  • Would use flask-sock or a small ASGI sidecar.
  • REST /api/ros/watch etc. remain regardless.
Browser Server │ GET /events (text/event-stream) │ ───────────────────────────────────► │ │ EventBus fan-out │ event: metrics.updated │ │ data: {aggregate:{…}} │ │ ◄─────────────────────────────────── │ event: node.changed │ │ data: {node:{id:755,status:…}} │ │ ◄─────────────────────────────────── │ (no polling, no 3 concurrent loops)│

9Frontend Strategy

Two viable directions — pick one per the team's appetite. Both start from the current server-rendered Bootstrap base.

Option A — Server-rendered + HTMX/SSE low risk

Keep Jinja templates; add HTMX for partial swaps and an EventSource listener that triggers HTMX hx-swap on the SSE events. Charts stay Chart.js.

Pros: minimal new tooling, reuses existing CSS/templates, fast to ship, great for ops dashboards.

Cons: less interactivity headroom long-term.

Option B — Lightweight SPA more headroom

Preact/Petite-Vue or vanilla Web-Components SPA against the OpenAPI REST + SSE stream. Flask becomes a pure API.

Pros: decoupled UI, better state handling, easier to add control panels.

Cons: build pipeline, more surface area, must re-implement the 7 current pages.

Recommendation

Start with Option A (HTMX + SSE) to deliver the real-time win quickly while preserving the existing look, and treat the SSE event schema as the stable contract that makes a future SPA (Option B) a drop-in.

9.1 Immediate UI cleanups (either path)

  • Remove the dead template/ directory (duplicate of templates/).
  • Move per-page JS out of inline <script> into static/js/* modules.
  • Stop rendering latency as a pre-formatted string on the model — render from numbers in the template.
  • Unify the 3 polling loops behind the SSE client.

11Observability

Structured logging

  • JSON logs with node_id, event, trace_id fields.
  • Kills get_node_log_lines regex: the /api/logs/{node} query filters structured records instead of grepping a flat file.
  • Rotation + size caps via stdlib RotatingFileHandler.

Health & metrics

  • /health = liveness (process alive); /ready = readiness (ROS connected / agent reachable).
  • Optional /metrics Prometheus endpoint (request rates, event lag, ROS spin errors).
  • Docker stats collector kept as a host adapter publishing MetricsEvent.

12Security

  • Session auth (Flask-Login) replacing single-user HTTPBasicAuth; hashed passwords in DB.
  • Roles: viewer (read + SSE), operator (watch/unwatch, ack failures), admin (node status changes, config).
  • CSRF protection on all state-changing forms/requests.
  • Audit log: who changed which node / acked which failure (stored next to failures).
  • Keep existing rate limiting; route /events through a per-IP connection cap.
  • Secrets remain env-driven (SECRET_KEY, ADMIN_PASSWORD); never committed.

14Migration Plan (incremental, always-green)

1

Stabilize & clean

~2 days · risk: low

Delete dead template/ dir. Move inline JS to static/js. Hoist magic constants (ROS_WATCH_LIMIT, ROS_SAMPLE_HISTORY_LIMIT, history depth) into config. Extract TopicTelemetryState + clock-mapping into testable modules. No behavior change.

2

StateStore + app factory

~3 days · risk: medium

Introduce create_app(), move globals behind StateStore, convert the ros_update_callback switch into typed events. Route handlers delegate to the store. Existing templates keep working against snapshots. Fix the gunicorn-starts-ROS bug via lifecycle hooks.

3

Persistence + health

~2 days · risk: low

SQLite repository for nodes/failures/metrics-snapshot. State survives restart. Split /health vs /ready. Structured JSON logging; replace log-grep with structured query.

4

Real-time (SSE) + UI

~3 days · risk: medium

EventBus + /events SSE. HTMX partial swaps driven by EventSource. Retire the polling loops. Surgical DOM updates for watched topics. The big visible win.

5

API + auth polish

~2 days · risk: low

RESTful verbs + OpenAPI/Swagger UI. Session auth + roles + CSRF + audit log. Backwards-compatible aliases for the old endpoints during transition.

6

Adapter generalization

~2 days · risk: low

Formalize NodeAdapter protocol; the Renode bridge becomes one impl. Prepares for additional boards / a real-hardware adapter without touching the dashboard.

Always-green guarantee

Each phase ends with a deployable dashboard. Phase 1 is pure cleanup; phase 2 keeps templates working; the real-time layer (phase 4) is additive until the polling loops are removed. Rollback at any phase = revert one PR.

⚠ SSE + gunicorn note

SSE holds a connection open per tab, which doesn't play with the default prefork sync model. Use gthread workers (or a small gevent pool) for the /events route, and document the worker count in docker-compose. This is a deployment note, not an architecture risk.

16Testing Strategy

Unit (no ROS, no Docker)

  • StateStore.apply for every event type → correct snapshot + derived events.
  • Clock-mapping & latency math (extracted from bridge) with synthetic time-sync samples — currently untested.
  • Failure ID stability, status transitions, watch-limit enforcement.
  • SQLite repository round-trips.

Integration & contract

  • NullRosService + fake event feed drives the full app; assert REST + SSE output.
  • OpenAPI schema tests (every route documented; response models match).
  • Backwards-compat aliases for renamed endpoints.
  • Docker-compose smoke test: agent + bridge + dashboard boot, a simulated heartbeat appears via SSE.

Target: ≥80% coverage on non-rclpy code (rclpy paths covered by the NullRosService integration tests).

Open questions for review

  1. Frontend path — confirm HTMX+SSE (Option A) vs committing now to an SPA (Option B)?
  2. Persistence — SQLite acceptable, or is Postgres preferred on the Jetson deployment for shared state across services?
  3. Auth scope — is multi-user/roles in scope for v2.0, or defer to v2.1 and keep single-admin with stronger hashing/session for now?
  4. Adapter scope — is a second (non-Renode) node adapter imminent, justifying phase 6 now?
  5. OpenAPI tooling — preference between flask-smorest (decorators, full) vs apispec (lighter, manual)?
